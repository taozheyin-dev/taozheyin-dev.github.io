01

先把边界说清楚

先明确输入、输出和失败方式，再写适配。不同协议的差异应有固定的处理位置。

02

用证据缩小问题

从日志和实际载荷出发，构造能复现问题的最小场景，每次只改变一个关键变量。

03

让配置可以追踪

把模型、路由与环境配置纳入版本管理，保留变更原因，也为回退留下路径。

04

交付包含验证

根据改动检查关键行为，记录限制和使用方式，让下一次维护有据可依。

CodeBuddy2API

每日活动流程与可靠性

开源贡献 · 已合并至上游

项目将 CodeBuddy / WorkBuddy 订阅接入 OpenAI 兼容接口。我的贡献集中在国际版 WorkBuddy 的每日活动流程。

上游项目 ↗贡献 PR #52 · 已合并 ↗我的 Fork ↗
系统流程示意

要解决的问题

活动流程涉及会话连接、异步准备和每日执行状态。发送状态不清楚时，重试可能造成重复执行；时区或调度处理不当，也会导致任务遗漏或集中触发。

我的贡献

  • 实现 ACP 会话客户端与每日活动调度，按账号和本地日期记录执行预留，功能默认关闭、按需启用。
  • 区分未发送、已发送和待确认状态，保留未发送任务的重试机会，避免重放已发送但未确认的请求。
  • 补充回归测试，修复日期边界、账号分时调度、记录清理与异步沙箱准备等问题。

实现结果

PR #52 于 2026 年 10 月 4 日合并至上游。PR 正文记录了离线回归测试、真实账号验证及相关环境限制，可直接查看原始验证材料。

工程取舍

协议调用返回不代表业务任务已经完成，因此需要从控制台读回完成状态。对已发送但未确认的请求停止自动重放，会保留待确认状态，也降低了重复执行的风险。

NIM Proxy

同模型请求竞速与部署

个人 Fork 开发 · Fork 内 PR 评审中

上游是 Rust 编写的 OpenAI 兼容代理，提供限速与多密钥调度。我在个人 Fork 中开发同模型请求竞速及相关部署流程，改动尚未合入原项目上游。

上游项目 ↗我的 Fork ↗Fork 内 PR #1 ↗
系统流程示意

要解决的问题

冗余请求可能降低等待时间，也会增加上游消耗。多个尝试并行时，需要保持用户指定的模型、共享限速约束，并明确响应归属和取消边界。

我的贡献

  • 为同一模型的相同请求增加立即或延迟的冗余尝试，选择首个有效响应，并取消落败尝试。
  • 修复竞速中的密钥授权、记账和响应边界问题，让每次发送仍经过共享限速机制。
  • 整理普通流量与可选竞速流量的双通道部署、运行手册和验证记录。

实现结果

实现与部署记录集中在个人 Fork 的 PR #1，当前处于评审阶段。PR 包含测试、合成负载和真实路由验证记录，也列出了已知限制；真实环境的加速效果仍需进一步测量。

工程取舍

只对同一模型发送冗余请求，保留用户选择的模型语义。代价是额外的请求消耗，需要同时控制限速、延迟触发、取消与清理，不能只关注最早返回。

AI 服务导航

公益 AI 中转站目录

个人网站 · 内容与工程维护

个人维护的公益 AI 中转站导航网站，使用原生 HTML、CSS 与 JavaScript 实现，并通过 GitHub Pages 发布。

访问网站 ↗项目仓库 ↗
系统流程示意

要解决的问题

不同站点的注册方式、奖励规则和可用模型分散在各处，而且会持续变化。导航需要清楚呈现这些信息，并及时处理变更与失效入口。

我的贡献

  • 整理站点分类、注册方式与服务说明，持续收录、修订条目并归档失效站点。
  • 实现中英文切换，调整英文内容和统计脚本的加载时机，减少首屏加载的负担。
  • 维护 GitHub Pages 部署，以及图标、站点元数据和一致性检查等构建脚本。

实现结果

站点可公开访问，目录与页面持续维护。仓库保留了内容更新、语言切换与加载方式调整的提交记录。

工程取舍

静态页面让部署保持简单，但目录有效性、图标与元数据需要持续维护。英文内容按需加载减少了首屏请求，也需要处理首次切换时的等待。
